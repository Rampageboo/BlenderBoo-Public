# v0.6.3 Plan: Assembly Analysis, Fast Capture, Background Render

Status: Owner-approved direction, 2026-09-24. Start after
`docs/v0.6.2-exec-change-detection-and-detail-review.md` is complete, and
build on it (Part C close-ups and Part D deployment there). If v0.6.2
deployment has already happened, redeploy with the same steps at the end.
Names and shapes are proposals; the "Decided" items are not.

## Why

Detail fails most visibly at part interfaces. In the M4A4 lower receiver the
trigger guard is a round tube whose ends end inside the receiver and magwell
with no mounting structure; whether the parts touch, have gaps, or
interpenetrate can currently be judged only by eye. Comparable projects
(glonorce/Blender_mcp BVH assembly analysis; PatrykIti/blender-ai-mcp
`scene_measure_gap` / `scene_assert_contact`) measure this deterministically.
The agent also needs a cheap, frequent look at its work, and long renders
must stop blocking Blender's main thread.

## Decided

- Assembly analysis uses real mesh surfaces (evaluated, world space), not
  bounding boxes. Bounding boxes are only a candidate-pair filter.
- All GPU/viewport capture stays on the deferred draw-handler path
  (`05-risks-and-gotchas.md`). Nothing GPU-related runs in the bridge timer.
- Background renders never render the live document in-process; they render a
  saved copy in a separate Blender process.
- No numeric "quality score". Report measurements and pass/fail against
  explicit expectations.

## Part A: `assembly.analyze`

### Input

- Scope: explicit pairs `[[a, b], …]`, or a list of objects / a collection
  from which candidate pairs are chosen.
- Candidate filter: world bounding boxes expanded by `search_margin` (default
  proportional to scene scale, e.g. 1% of scope diagonal, overridable in
  metres); prefer parent/child and same-collection pairs first; cap pairs
  (`max_pairs`, default 200) and report skipped pairs.
- Tolerances: `contact_tolerance` (distance treated as touching),
  `max_faces_per_object` budget (refuse or decimate-for-analysis with a
  warning; never modify the scene).
- Optional expectations per pair: `contact`, `gap_between: [min, max]`,
  `no_intersection`, `intersection_allowed` (for intentional press fits).
- Uses evaluated geometry (modifiers applied) by default; `evaluated: false`
  for base mesh.

### Method (executor may improve)

Per object: `mathutils.bvhtree.BVHTree.FromObject` on the evaluated
depsgraph, transformed to world space. Per pair:

- **Intersection:** `BVHTree.overlap` → overlapping face pairs. Estimate
  penetration depth by sampling vertices of each mesh that lie inside the
  other (closest-point normal sign or ray parity) and taking the max distance
  to the other surface. Report overlap face count, max depth, and a
  representative world location.
- **Gap / contact:** minimum surface-to-surface distance using
  `find_nearest` from sampled vertices (and face centers when needed) of the
  smaller mesh against the larger BVH, both directions. Report `min_gap`,
  closest point pair (world coordinates), and, within `contact_tolerance`,
  approximate contact region (sample count, bounds).
- **Status:** `intersecting` | `contact` | `gap` | `separated` (beyond
  margin), plus `expectation: pass | fail` when an expectation was given.

### Output (default receipt)

Only pairs that are `intersecting`, `contact`, `gap`, or failed an
expectation; separated pairs as a count. Each pair includes a
`focus` = `{point, radius}` that Part C close-up render (v0.6.2) accepts
directly, so the agent can look at the exact joint in one more call.

### Tests

- Unit (pure Python, fake BVH): status classification, expectation logic,
  candidate filtering and caps.
- Headless 5.2 with constructed fixtures: two cubes 1 mm apart (gap),
  touching (contact), overlapping by 2 mm (intersecting, depth ≈ 2 mm within
  tolerance), a curved tube ending inside a box (intersecting at the tube
  end), and a parented pair. Evaluated vs base geometry with a Solidify
  modifier.
- Performance: two 200k-face meshes analysed within a reported time; record
  it in the PR.

## Part B: fast capture for frequent self-checks

Goal: an agent can check its work after most edits without paying render
cost.

- Measure current `scene.screenshot` latency (bridge round trip, draw
  callback, PNG write) at 512 and 1024 px. Report the numbers.
- Provide a fast mode: viewport-quality OpenGL/offscreen draw (solid or
  material preview shading, overlays optional, wireframe overlay optional),
  targeted framing reusing v0.6.2 Part C (object, objects, point+radius,
  bbox; ortho or perspective), low default resolution (e.g. 512 px long
  edge), and several views composed into one contact sheet in a single call.
- Target: p50 ≤ 500 ms end-to-end for one 512 px view on the test scene;
  if not achievable on the deferred path, report the measured floor and why.
- Return the image through the MCP image channel plus a small text receipt
  (path, view parameters). No base64 in text.

Tests: headless where possible for framing and sheet composition; a live GUI
test for the draw path, including two concurrent clients (GPU risk rule).

## Part C: background render in a separate process

Goal: final-quality renders and bakes that take seconds to minutes no longer
block the live Blender or time out ambiguously.

### Flow

1. Tool call (e.g. `render.background` with the same camera/target/output
   options as the preview/review tools, and later `bake.run` via the same
   runner) returns immediately with an operation ID.
2. On the main thread: save a copy of the current document
   (`save_as_mainfile(copy=True)`) to a temp path; record whether the live
   document was dirty. Make external file paths absolute in the copy (or pass
   `--python-expr` fix-up) so textures resolve.
3. Launch `bpy.app.binary_path -b <copy> --python <runner>` with a JSON job
   file (camera, framing, engine settings, output path, overwrite policy).
   The runner writes progress (frame/samples when available) and a final
   result JSON next to the output.
4. Status is queryable through the operation-ID mechanism from v0.6.1
   Part E (queued/running/succeeded/failed/cancelled, elapsed, output
   paths). Cancellation kills the child process; this **is** real
   cancellation, unlike in-process operations.
5. Clean up the temp copy after completion; keep it on failure for
   diagnosis, bounded by a retention limit.

### Constraints

- Limit concurrent background jobs (default 1) and report queue position.
- Warn if the live document changed after the snapshot (the render reflects
  the snapshot, not later edits).
- GPU contention with the live Blender is expected; document it.
- Works for unsaved (never-saved) documents by snapshotting to temp.

### Tests

- Unit: job file generation, status transitions, cancellation, retention.
- Headless: render a small scene via the runner and verify output
  dimensions; cancel a long render and verify the child process exits and
  status is `cancelled`; snapshot of a dirty document renders the unsaved
  change.

## Part D: tool descriptions and server instructions carry tool knowledge

Direction (Owner, 2026-09-24), following Anthropic's Claude 5 context
engineering guidance (rules → judgment; interface design over examples; tool
guidance in tool descriptions, not repeated in prompts) and OpenAI's GPT-6
Astra skill guidance (short specific triggers; soften boundary language that
capable models over-apply; define done).

The skill `skills/blender-codex-modeling/` has been reduced to a definition
of done. Everything an agent needs to know about **how the tools behave** now
belongs in the MCP surface, so it is present whether or not the skill loads.
The removed reference files are in git history (`git show 071343b:skills/blender-codex-modeling/references/<file>`)
and are the source material for this part: `python-exec.md`,
`tool-boundaries.md`, `response-compression.md`.

### Server instructions (`_SERVER_INSTRUCTIONS` in `server.py`)

Rewrite as a short set of facts with reasons, no rule lists. Must cover:

- one Blender instance per task; name it explicitly when several are
  registered, because calls otherwise route ambiguously;
- after a timeout or transport failure a mutation or exec may have completed
  or still be running (Blender's main thread cannot be interrupted), so
  inspect before repeating it;
- typed tool when it fits, `python.exec` otherwise;
- fast captures and close-ups are cheap and are the intended way to check
  work frequently (Part B, v0.6.2 Part C).

Remove the current sentence that screenshots should be called "only when
explicitly requested" and to "avoid intermediate captures"; it contradicts
the frequent visual check loop this release builds. Remove "Never
automatically retry …" wording in favor of the fact above.

### Tool descriptions

- `python.exec`: namespace, `result` convention, stream caps, `changes` and
  `detection` semantics (v0.6.2), `checkpoint`, `view3d_override`, and the
  hazards as facts with the safe alternative: GPU/render calls inside exec
  can crash Blender because exec runs in the bridge timer — use the capture
  and render tools; file switches or add-on reloads invalidate bridge state;
  a running script cannot be cancelled.
- Every tool with a non-obvious limit states it in its own description
  (e.g. `architecture.wall_build` junction behavior, `workflow.run` step cap
  and synchronous nature, `collection.transform` member limits, response
  artifact lifetime in `response.artifact_get`).
- Replace absolute prohibitions in descriptions and error messages with the
  consequence and the alternative. Keep hard refusals in code where they
  protect data (confirmation gates, state tokens); wording is what changes.
- Keep descriptions short; do not add usage examples unless a parameter
  cannot be made self-explanatory.

### Acceptance

- `adapter.schema_audit` aligned; description text is identical between
  add-on and adapter where both define it.
- A test asserts `_SERVER_INSTRUCTIONS` contains no "only when explicitly
  requested" / "avoid intermediate captures" guidance and stays under a
  byte budget (suggest 1,200 bytes).

### Tool discovery mode

Claude Code defers MCP tool schemas and loads them through its own tool
search; Codex reportedly does the same when `tool_search` is available
(openai/codex issue #14507). Client-side deferral gives what search mode
(`toolsets.list/describe/call`) was built for, while keeping per-tool typed
schemas at the call site. Therefore:

- Keep `eager` as the default. Keep `search` mode as a fallback for clients
  that load every schema up front; do not remove it.
- Verify after deployment, in both a fresh Codex session and a fresh Claude
  Code session: are codex-blender tools deferred (not all schemas in the
  initial context)? Record the initial context usage with eager mode in
  `docs/v0.6.3-validation.md`. If a client does not defer, set
  `CBT_MCP_TOOL_MODE=search` in that client's config only.
- Deferred search matches on tool names and descriptions, so the short,
  specific descriptions required above also determine whether the agent
  finds the right tool.
