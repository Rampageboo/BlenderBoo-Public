# v0.7 Plan: Creature Modeling, Retopology, and Rig

Status: Owner-approved direction, 2026-09-25. Supersedes the human-only draft.
Start after v0.6.4 (deployed). This reverses the 2026-07-17 decision that
deprioritized retopology; record that in
`project-context/sources/04-decisions.md`. Names and shapes are proposals;
the "Decided" items are not.

## Goal

Turn an organic creature — humanoid, quadruped, reptile/tailed, or other —
into a game- and animation-ready asset: clean deliberate topology within a
budget, a skeleton, game-valid weights, maps baked from the source, and
measured deformation quality. Human characters are one body plan of this
pipeline, not a separate one.

## Decided

- **The shape source is not the deliverable.** Typical source: a Tripo 3D
  (or other AI-generated, scanned, or sculpted) high-poly mesh. It is used as
  the target for fitting and baking, never shipped, and never modified in
  place.
- **Topology is built, not cleaned.** Clean topology comes from (1) a base
  mesh generated from a body graph and fitted to the source, or (2) wrapping a
  template when one exists for that body plan. Automatic remeshing
  (Quadriflow etc.) is only a fallback and is flagged as such in results.
- **Body graph first.** A creature is described by a graph of named joints
  (position, radius, parent, symmetry pair). The same graph drives the base
  mesh, region masks, and the skeleton, so mesh and rig agree.
- **Topology is invariant after fitting starts.** Fitting moves vertices
  only and proves counts and connectivity unchanged.
- **Skeletons:** humanoids can target the UE Mannequin exactly (names,
  hierarchy, orientation conventions from the Owner's exported Mannequin FBX);
  other body plans use a custom skeleton following UE conventions (single
  root, consistent orientations).
- **Game constraints:** no n-gons in the export, per-asset triangle budget,
  bounded influences per vertex (default proposal: 4).
- Every stage returns measurements and `focus` points for `render.detail`.

## Owner inputs

- Tripo exports (GLB/FBX/OBJ with textures when available). For rigging,
  generate in a neutral pose: limbs separated from the body, fingers/toes
  apart, mouth closed, A- or T-pose for humanoids. Fused limbs and baked
  lighting in textures make fitting and baking worse; the intake step reports
  them. Check Tripo's licence terms for the intended commercial use.
- Per asset: body plan, triangle budget, influence limit.
- For humanoids targeting UE: UE version and the exported Mannequin
  skeleton FBX (Manny or Quinn).

## Part 0a: form-perception views (do first; also serves hard-surface)

Lit renders mix form with lighting and material, and a grayscale depth image
is hard for a vision model to read quantitatively. Add views that isolate
surface form.

Current state: `scene.fast_capture` has `shading: current | solid | material`
plus `overlays` and `wireframe`; `render.detail` and `render.ortho_set` have
no shading control.

Add a `view_mode` parameter to `scene.fast_capture`, `render.detail`, and
`render.ortho_set` (and let `render.contact_sheet` label it):

| `view_mode` | Shows | Typical use |
|---|---|---|
| `lit` | current behavior (default) | overall look |
| `normal` | surface orientation, lighting- and material-independent (viewport normal/matcap or a normal pass) | faceting, bevel roundness, recess depth, surface flow |
| `matcap` | neutral clay-like studio matcap | silhouette and form reading |
| `curvature` | convex/concave highlighting (cavity or a curvature attribute) | panel lines, creases, muscle and wrinkle definition |
| `depth` | depth as a color heat map **with a legend and numeric near/far range** (never unlabeled grayscale) | relative depth of features |
| `wireframe_on_shaded` | edges over the chosen shading | topology review for creatures |

Requirements:

- All on the existing deferred draw/render paths; no GPU work in the bridge
  timer.
- Deterministic: fixed matcap and color ramps shipped with the add-on, so
  images are comparable across runs and versions.
- The receipt states the mode and, for `depth`, the numeric range and units.
- Restore every viewport/shading setting afterwards (covered by the existing
  concurrent-client GUI smoke test).

Tests: headless or GUI smoke per mode on a fixture with a bevelled cube, a
faceted low-poly sphere, and a recessed panel; assert image dimensions,
receipt fields, and restored settings; a pixel check that `normal` output
differs between faceted and smooth-shaded spheres.

Deferred (not in this plan): comparing model depth against depth estimated
from reference photos. Revisit only if contour matching passes while interior
form is still measurably wrong; it needs an external depth model (check its
licence) and scale calibration, and is weak on glossy or dark surfaces.

## Part 0b: fixes from the first full 0.6.4 session (do before Part A)

Evidence: M4A4 session, 2026-09-25 07:15–10:14 UTC, 410 unique call-log

1. **Make the edit cycle lighter.**

     rejects when *another* client holds one), yet the agent acquires and
     releases one every cycle. State in the lease tool descriptions and
     server instructions when a lease is useful (several clients on one

   - `scene.save_current` defaults to `dry_run: true` and requires
     `confirm`. For an in-place save of a document that already has a path
     and whose file on disk is unchanged since it was opened or last saved,
     allow one call. Keep the gate when the disk file changed externally or
     a path is being created.
   - `session.call_log_summary`: default to a compact summary; add
     `since_seq` (delta since a previous summary) and `detail` levels, so an
     agent writing stage notes does not pull the full table every cycle.
2. **The 0.6.4 reference tools were never used.** Zero calls to
   `camera.calibrate_from_reference` or `render.contour_compare`; the agent
   kept approximating photo cameras by hand. Likely causes, to verify:
   pixel correspondences are hard for an agent to produce from photos, and
   the tools are not surfaced where the modeling workspace looks.
   - Make the path discoverable: `render.reference_match` description and
     receipts point to calibration when no calibrated camera is used; server
     instructions name the calibrate → contour loop.
   - The modeling thread confirmed both tools work and that not using them
     was a workflow omission, not a missing capability. Discoverability is
     the fix, not new calibration math.
   - **Import photogrammetry cameras** (`camera.import_photogrammetry`): the
     Owner's references come from RealityScan with a point cloud. Import
     registered camera poses and intrinsics in the same frame as the
     imported point cloud, with a similarity transform to the model. Exact
     reference alignment still requires pixel validation against known
     image/3D correspondences.
     - **First format: RealityScan camera CSV (standard GUI export).**
       Header
       `#name,x,y,alt,yaw,pitch,roll,f_35mm,px_norm,py_norm,k1,k2,k3,k4,t1,t2`.
       Paths are parameters; never hardcode the Owner's workspace.
       **Current baseline (2026-09-25 re-alignment):**
       `NoCP_NoDist_UnknownCalib_404.csv` — 404 registered cameras of ~499
       frames, distortion fixed at zero (all `k`/`t` = 0), focal free
       (`f_35mm` 25.2–58.0, median 45.2), principal point still free
       (offset > 5% of image size on 70 cameras, > 10% on 9). Matching point
       cloud: `M4A4_CP7_CameraCLean.ply` (exported after the CSV; confirm it
       is from the same alignment before use). Per-frame AI masks exist in
       `Mask/` (499, named `<image>.png.mask.png`). Older exports
       (`M4A4_CP7.csv`, `M4A4_CP7_Fixed.csv`, `M4A4_CP7.ply`) are superseded;
       their frames differ and they must not be mixed with the baseline.
     - **Conventions are not documented in the file; determine them
       empirically, not by assumption.** Candidates: `x, y, alt` camera
       centre in the project frame; `yaw, pitch, roll` in degrees with an
       unknown axis order and zero reference; `f_35mm` = focal length in a
       36 mm-wide equivalent; `px_norm, py_norm` principal-point offset as a
       fraction of image size. Choose the convention by projecting the
       exported point cloud into several images and minimizing the
       reprojection error against the image content (or masks when present);
       report the chosen convention and its error. Do not hardcode a guess.
     - **Frame to Blender:** the inspected `D:/M4A4/M4A4.blend` has the original
       RealityScan mesh at identity, but no object matching the exported
       61,212-point cloud. Select or import a known-aligned mesh/cloud object,
       then apply its world similarity to the cameras. RealityScan OBJ exports
       keep the camera frame only when imported with forward = Y, up = Z;
       Blender's default OBJ axis conversion misplaces them (verified by the
       Camera Refinement Workbench: Blender silhouette vs workbench at IoU
       0.990, all differences within 1 px, with explicit axes). The importer
       must state and test the axis choice.
     - **Focal length varies legitimately; distortion does not.** The images
       are frames of a game capture in which the Owner zoomed in on details,
       so per-image `f_35mm` (8.9–58.6, median 45.4) can be real. Game
       rendering has no lens distortion, so the solved distortion (`k2` −507
       to 1438, `k3` −86,838 to 11,391) is solver compensation, not optics.
       The source video has no distortion. The importer must:
       - keep per-image focal length;
       - **keep focal, principal point, and pose from one solve together.**
         Poses were fitted jointly with those intrinsics; replacing either
         while keeping the pose breaks the fit. A Blender camera cannot apply
         the raw CSV distortion, so a distorted CSV import is diagnostic;
         use an undistorted workbench handoff for matched-view evaluation.
         Measured on the M4A4 baseline (Camera Refinement
         Workbench, 11 frames): RealityScan's solved principal points give
         median IoU 0.977 and ~1.15 px mean outer-boundary error against the
         AI masks; centring the principal point with the same poses drops
         median IoU to 0.627 and the error to ~33 px.
       - If a solve has nonzero distortion, warn and use undistorted reference
         images from the workbench rather than silently claiming an exact
         Blender camera. The workbench handoff baseline has none.
       - Report per camera: principal-point offset, focal, and any stated
         quality metrics from the source, so the agent can choose reference
         frames; flag focal jumps inconsistent with neighbouring frames.
       - Record the camera set's kind on the imported cameras:
         `reproduction` (a solve's intrinsics and poses exactly as solved,
         e.g. RealityScan) or `constrained` (re-optimized under physical
         constraints, e.g. centred principal point, by the Camera Refinement
         Workbench). Never mix intrinsics from one kind with poses from the
         other; keep both sets side by side when both exist.
     - **Principal point is physically centred for this footage** (fixed
       in-game camera, rotating weapon, in-game wheel zoom, no occluders; a
       zoom-pair check on frames 88→93 fits a centre-anchored scale of
       1.4078 against a focal ratio of 1.4072 with 0.45 px median residual).
       RealityScan's per-frame offsets compensate other solve errors, but its
       cameras still reproduce the images to about 1 px, which is what
       model evaluation needs. Use them as solved. A centred camera set is
       only valid when it comes from a solve constrained to a centred
       principal point. The Camera Refinement Workbench now has a centred
       plateau solve with 404 cameras and 51-frame silhouette quality near
       the RealityScan reproduction; it is a candidate, not the default.
     - **Camera solving is out of scope for this toolkit.** A constrained
       re-solve (COLMAP game-pinhole model, FOV-vs-dolly focal experiment,
       mask handling, optional silhouette refinement against trusted meshes)
       belongs to the Owner's separate Camera Refinement Workbench project.
       The toolkit imports its `cameras.json` handoff package or exported
       COLMAP text model (see "Second format" below), retaining per-camera
       quality metrics when supplied.
     - **Never refine reference cameras against the model being built.** If
       cameras were refined, the import records against which mesh; the
       toolkit only measures the model under evaluation (IoU / boundary
       distance via `render.contour_compare`) with independently solved
       cameras. RealityScan AI masks have jagged edges and slight background
       leakage, so boundary errors below the mask's edge uncertainty are
       reported as not meaningful.
     - Only frames used as modeling references need the highest accuracy;
       surface per-camera quality so the agent can pick good frames.
     - Commit a small sanitized fixture (a few rows, renamed images, a
       point subset) for tests.
     - Verification: import the cameras, render the model/point cloud from
       an imported camera, and overlay on the matching photo; reprojection
       of known points must fall within a stated pixel tolerance. Distortion
       is reported and optionally applied to the overlay (undistort the
       photo), since Blender cameras have no lens distortion.
     - **Second format: Camera Refinement Workbench handoff**
       (`cameras.json` with per-camera scores), or a COLMAP text model
       (`cameras.txt`, `images.txt`, optional `points3D.txt`). The latter
       imports sparse points on request; the former supplies scores directly.
       Metashape XML / RealityScan XMP only when needed.
     - **Convention test first:**
       before any other work, prove with synthetic cameras that a known 3D
       point projects to the same pixel through the importer and through a
       Blender render, for both formats, including focal conversion
       (`f_35mm` against a 36 mm sensor width, horizontal fit) and the
       camera axis convention.
   - Help correspondence picking when there are no photogrammetry cameras:
     a zoomable crop/grid view of the reference image so the agent can read
     pixel coordinates reliably.
3. **Point-cloud comparison as typed tools.** The agent hand-wrote ROI
   selection, sectioning, and distance checks against the scan every time.
   - `pointcloud.section`: slice a point cloud (and optionally a mesh) with
     a plane and band width inside an ROI; return the 2D section points,
     a fitted polyline, and the mesh section for comparison, with an image.
   - `mesh.compare_to_points`: distance from points to mesh surface within an
     ROI, with outlier/noise filtering and density report; stats, a heat-map
     image, and worst regions with `focus`. Report sparse regions as
     undetermined rather than as error.
4. **Catch silent geometric collapse.** A Boolean reduced a part to 7 faces
   while the API succeeded; only a render revealed it. Add to `python.exec`
   `changes` (and typed mesh mutations) per-object face count, bounding box,
   and volume (closed meshes) before/after, with a
   `suspicious_change` warning for large relative drops or bounding-box
   jumps (thresholds configurable). Informational, never blocking.
5. **Tiny faces after bevel.** A bevel produced 93 tiny faces that needed
   hand-written cleanup. Fold into Part E: `mesh.topology_report` finds

8. **Call log: separate execution from acceptance, record versions.** Each

## Part A: source intake — `source.inspect`, `source.prepare`

- `source.inspect` (read-only): triangle count, islands and their sizes,
  non-manifold/boundary edges, self-intersections (reuse v0.6.4 BVH logic),
  estimated symmetry plane and asymmetry score, bounds and scale, texture
  maps present, pose hints (limb-to-body proximity that suggests fused
  limbs).
- `source.prepare`: creates a separate **projection proxy** — remove small
  islands, close holes, voxel remesh to watertight at a chosen resolution,
  optionally symmetrize — while keeping the original untouched for color and
  detail baking. Reports what changed and the proxy-to-original distance.

## Part B: landmarks and body graph

- Landmark sets per body plan stored as data files (humanoid, quadruped,
  reptile/tailed); the Owner approves each set. Landmarks are Empties with a
  custom property naming the landmark, placeable by tool or by hand.
- `creature.graph_suggest`: propose a body graph from landmarks plus the
  proxy — joint positions from landmark rules, radii by slicing or ray
  casting the proxy at each joint plane, symmetry pairs mirrored. Returns
  confidence per joint and never applies without an explicit apply.
- `creature.graph_set` / `graph_inspect`: store the graph on an object
  (custom properties or a JSON text datablock), editable by the agent.
- Appendages not in the body plan (horns, spikes, fins, extra limbs) are
  either added to the graph as branches or recorded as separate parts to be
  modeled with the hard-surface tools and parented to a bone. The graph
  records which.

## Part C: base mesh from graph — `creature.base_from_graph`

- Generate a quad-dominant base mesh from the graph (Skin modifier or an
  equivalent), with per-segment control of loops around (circumference) and
  along (length), extra loops at joints, and symmetric output.
- Assign region vertex groups per graph segment (for masks, detail, and
  weight initialization).
- Output a topology report (Part E) and the loop counts at each joint.

## Part D: fit — `mesh.wrap_to_target`

Generic for any fixed-topology mesh onto a target (graph base or template
onto the proxy):

1. similarity alignment from landmark/graph pairs;
2. non-rigid landmark deformation;
3. iterative projection with Laplacian or as-rigid-as-possible
   regularization, symmetry constraint optional, per-region stiffness;
4. relax on surface.

Output: distance fitted→proxy and proxy→fitted (coverage: source regions the
mesh does not reach, e.g. an unmodeled horn), landmark residuals,
flipped/collapsed faces, face-quality change, **topology proof**, worst
regions with `focus`. Result is a new object.

## Part E: topology diagnostics — `mesh.topology_report`

Read-only, generic (also useful for hard-surface):

- quads/triangles/n-gons, budget check;
- poles by valence with positions and region, and whether any pole lies in a
  joint bend zone (from graph);
- loop tracing: closed loops around each joint and count of loops across
  each bend zone (thresholds per body plan, Owner-editable);
- symmetry map and max asymmetry;
- face-quality distributions; connectivity hash.

## Part F: skeleton

- `armature.from_body_graph`: create bones from the graph with a naming
  scheme. For humanoids with a UE target, map graph joints to Mannequin bones
  using the imported reference FBX and keep its names, hierarchy, roll/axis
  conventions, and auxiliary bones (root, IK, twist). For other plans, a
  custom UE-convention scheme (root, spine chain, limb chains, tail/neck
  chains).
- `armature.validate_against_reference` when a reference exists; otherwise
  structural checks (single root, no zero-length bones, chains continuous,
  joints inside the mesh volume).
- UE skeletal-mesh FBX export preset and a round-trip re-import check.

## Part G: weights

- Automatic weights on the clean fitted mesh (heat weighting works far better
  on clean manifold topology than on the source), initialized per region from
  graph vertex groups where helpful.
- `skin.weights_limit`: max influences, prune threshold, renormalize.
- `skin.weights_transfer_by_index` for template-derived meshes (refuses on
  connectivity-hash mismatch).
- `skin.validate` extensions: unweighted vertices, weights on non-deforming
  bones, influence histogram.

## Part H: bake from the source

Use `bake.run` (selected-to-active, cage or ray distance) from the
**original** source (not the proxy) to the fitted mesh: normal, AO, base
color from the source texture when present. Report coverage and warn when the
source texture appears to contain baked lighting (strong luminance gradients
consistent with a single light direction), because that lighting would be
baked into the albedo.

## Part I: deformation QA — `rig.rom_test`

- Range-of-motion pose sets per body plan as data (humanoid limbs/spine/
  neck/fingers; quadruped legs/spine/neck; tail and jaw where present),
  expressed in the skeleton's bone names; Owner-editable ranges.
- Per pose: local volume change near joints, max edge stretch/compression,
  self-intersections, twist collapse; worst per joint with `focus`, and one
  contact sheet of all poses via fast capture.

## Part J: humanoid template path (optional)

When the Owner approves a humanoid template (e.g. from a CC0 base mesh such as
MPFB2/MakeHuman after verifying its licence and topology), humanoids may use
template wrapping (Part D) instead of a graph base. Open questions for that
path: head/body split, facial topology.

## Skill: `blender-creature-modeling`

Write after the tools exist, against their actual behavior, following the
current skill guidance (short specific trigger, definition of done only;
tool behavior stays in tool descriptions). Done criteria to encode:

- silhouette and proportions match the source/concept in matched views;
- topology report within the body plan's rules (loops at bend zones, no poles
  in bend zones, no n-gons, within budget);
- fit distance and coverage within stated tolerance; missing appendages
  resolved;
- skeleton validates (against the Mannequin reference for UE humanoids);
- ROM test within thresholds, with the contact sheet reviewed;
- bake coverage complete; the source mesh is not part of the deliverable.

The hard-surface skill has been renamed `blender-hard-surface-modeling` and
its trigger excludes organic creatures. Deployment must remove the old
installed `blender-codex-modeling` copies (back up first; keep any local
`learning.jsonl`).

  within tolerance of the truth, with the topology proof holding.
- Unit tests for graph logic, topology metrics, loop tracing, symmetry,

- Headless 5.2 for each tool; FBX skeleton fixture for Mannequin validation

## Suggested order

Parts 0a and 0b first (independent, and they improve all modeling);
then A → B → C → E → D on the synthetic creature; then F, G, H, I; then the real
Tripo qualification; skill last. Part J only if the Owner provides/approves a
template.

## Out of scope

Facial rigs and blend shapes, clothing, hair/fur cards, LODs, UE-side import
settings beyond the FBX round trip, and choosing creature designs.
