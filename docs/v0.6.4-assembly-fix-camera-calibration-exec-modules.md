# v0.6.4 Plan: Assembly Fix, Reference Camera Calibration, Exec Modules

Status: Owner-approved direction, 2026-09-25. Builds on the committed and
deployed v0.6.3 (`2c23664`). Names and shapes are proposals; the "Decided"
items are not. Redeploy at the end with the v0.6.2 Part D steps.

## Evidence

From the first post-upgrade M4A4 rebuild (trigger guard, trigger, receiver
joints; call-log windows starting 2026-09-24T11:31Z and 12:04Z):

- `python.exec` carried 34–55% of calls and 77–94% of mutations. The
  modeling thread reported no case where a missing tool blocked modeling.
- Interface geometry (tabs, tongues, pin heads, recesses) was built as real
  editable geometry. Form matched the references only partially: opening
  edge, tab thickness, corners, and trigger profile still deviate, and the
  reference camera was placed by hand with no calibration, so no contour
  error could be measured.
- `assembly.analyze`: 18 checks, 8 failed; 7 of the 8 had no crossing faces.
  The thread re-checked the 8 deepest reported points with a 1 µm step and
  five directions and got zero "inside" votes.
- Each `python.exec` starts in a fresh namespace; helper libraries had to be
  reloaded every call (one NameError), and incremental edits are not
  replayable as a unit.
- `checkpoint.save` failed on the first call in several sessions
  (`InvalidParamsError`: `name_template` must contain base/index/tag), because
  the project naming convention is a fixed timestamped filename.
- A `render.background` job failed after a successful launch because a
  direction option was passed as a string array; the direct tools accept
  that form.

## Decided

- `assembly.analyze` never reports penetration shallower than
  `contact_tolerance`, and never reports penetration from a parity test on a
  surface that is not closed; it reports "undetermined" instead.
- Camera calibration reports its residuals. A calibration with high error is
  returned with the error, never silently accepted.
- Exec modules persist inside the `.blend` (so they travel with the asset),
  not in the add-on or a global folder.
- Background jobs validate their parameters synchronously; a launch that
  returns success must not fail later on a parameter error.

## Part A: fix `assembly.analyze` false penetration

Source: `addon/codex_blender_toolkit/tools/assembly.py`.

Defects (verified by reading source):

1. `_inside()` (line ~176) advances each ray by
   `epsilon = max(extent * 1e-8, 1e-9)` (≈10 nm, since `extent ≥ 1`). Blender's
   BVH works in single precision; at typical model coordinates the float32
   spacing is larger than 10 nm, so a ray can re-hit the same triangle and
   corrupt the parity count.
2. `_measure_pair()` (line ~237) treats any sampled point with
   `depth > 1e-8` that `_inside()` accepts as penetrating. Points lying on a
   flush or coplanar contact surface have float-noise depth and an
   ill-defined inside test, so contact becomes "intersecting".
3. Parity is meaningless against an open (non-manifold) target, but the
   code does not check closure.

Required behavior:

- Ray stepping: step at least ~1 µm scaled to model size (e.g.
  `max(1e-6, extent * 1e-6)`), and skip a hit on the same triangle index as
  the previous hit or within one step of the origin.
- Penetration requires the inside test **and** `depth > contact_tolerance`.
  Samples inside with depth ≤ tolerance count toward contact.
- Check whether the target evaluated mesh is closed (no boundary or
  non-manifold edges). If not, do not run parity; report
  `penetration: "undetermined"` with a warning naming the open object, and
  classify from distance and crossing faces only.
- Keep `_crossing_faces` as the evidence for transverse crossings, but
  require the crossing to extend beyond `contact_tolerance` on both sides
  before it alone classifies as intersecting.
- Report per pair which evidence drove the status (`crossing_faces`,
  `inside_samples`, `distance`), so a failed expectation can be audited.

Regression fixtures (headless 5.2), in addition to the existing ones:

- cylindrical pin seated in a hole with its end cap coplanar to a pin head
  face (the M4A4 "rear left pin head ↔ pin" case) → contact;
- flat tab flush against a wall, touching within 0.1 mm → contact;
- tab 0.05 mm into the wall with tolerance 0.2 mm → contact;
- 2 mm real overlap → intersecting, depth ≈ 2 mm;
- tube end inside a closed box → intersecting;
- open shell target with a crossing point → undetermined, warning;
- run each at model scale ~0.3 m and ~30 m to cover float spacing.

Also re-run the analysis on a copy of the M4A4 trigger checkpoint if
available locally; report how many of the 8 previous failures remain.

## Part B: reference camera calibration and contour error

Goal: turn "form matches the reference" into numbers the agent can drive
down.

### B1. `camera.calibrate_from_reference`

Input:

- reference image path;
- correspondences: list of `{pixel: [u, v], world: [x, y, z]}`, where world
  points can also be given as `{object, vertex_index}` or an Empty name
  (the Owner already marks positions with Empties);
- camera model: `perspective` (focal length unknown or fixed) or
  `orthographic` (scale unknown), optional principal point fixed at center;
- target camera name (create or update).

Method (executor decides): DLT / PnP with unknown focal length for
perspective (≥6 points; ≥4 with fixed focal), affine fit for orthographic
(≥4 points), then nonlinear refinement (Levenberg–Marquardt) with `numpy`
available in Blender. Set the Blender camera (location, rotation, lens or
ortho scale, sensor fit, shift) and render resolution/aspect to match the
image.

Output: camera parameters, RMS and per-point reprojection error in pixels,
the worst points, and a verification overlay (reference with projected
points and residual vectors) through the image channel. Fail with
`InvalidParamsError` for degenerate input (collinear/coplanar-insufficient
points), and warn when RMS exceeds a threshold relative to image size.

### B2. `render.contour_compare`

Input: calibrated camera, target objects, reference image, and a reference
mask source: a mask image path, or a threshold / chroma key / background
color rule for clean references. (No learned segmentation in this plan.)

Output:

- silhouette IoU;
- contour distance statistics (mean, p95, max) in pixels, and in model units
  when the camera is orthographic or depth at the contour is known;
- a deviation image (reference contour vs render contour, colored by
  distance) through the image channel;
- the top N deviation regions, each with a 3D `focus` (back-projected to the
  nearest model surface) that `render.detail` accepts directly.

Tests: synthetic scene rendered from a known camera as the "reference";
calibration recovers the camera within stated tolerances from exact and
noisy correspondences; contour compare reports ~0 for the identical model
and the expected deviation after moving/scaling one part by a known amount.

## Part C: persistent exec modules

- `python.module_put(name, code)`, `python.module_list()`,
  `python.module_remove(name)`. Store each module as a Blender text
  datablock (e.g. `cbt_module.<name>`) so it is saved in the `.blend`.
- Inside `python.exec`, `import cbt_modules.<name>` loads the stored text
  (custom importer or explicit loader), reloading when the stored text hash
  changed.
- The exec receipt lists the module names and hashes used; the call log
  records them, so a sequence of exec calls can be replayed exactly.
- Optional: `scripts/export_exec_log.py` writes the exec code sequence of a
  call-log window (with module texts) to a single replay script.

Tests: put → exec imports → edit → exec sees new version; save/reopen keeps
modules; removed module import fails with a clear error; hashes appear in
the call log.

## Part D: small contract fixes

1. `checkpoint.save`: accept a fixed filename or a template without
   `{index}`/`{tag}`; refuse to overwrite an existing file (unless an explicit
   `confirm`); retention (`keep_latest`) keys on an explicit
   `asset` identity when the name has no index.
2. `render.background` (and any background job, e.g. bake via the runner):
   normalize vector/direction options exactly as the direct tools do, and
   validate all job parameters before launching. Parameter errors return
   synchronously from the launch call.
3. Audit other tools for string-array vs number-array divergence between
   direct calls, workflow steps, and background jobs; one normalization
   helper for all three.
