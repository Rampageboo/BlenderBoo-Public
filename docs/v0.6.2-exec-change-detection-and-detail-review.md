# v0.6.2 Plan: Exec Change Detection, Exec Overhead, Detail Review, Deployment

Status: Owner-approved direction, 2026-09-24. Builds on the committed v0.6
(`55dc170`) and v0.6.1 (`576358d`) work. Names and shapes are proposals; the
"Decided" items are not.

## Why

1. `python.exec` reports `changed: false` for the edits that matter most for
   detail work. `tools/python_exec.py` snapshots only datablock identity/names
   and, per object, transform, parent, collections, modifier name/type, vertex
   and polygon **counts**, and material names. Moving vertices with bmesh,
   bevel/shape tweaks that keep counts, modifier property changes, material
   or Geometry Nodes tree edits, UV edits, attribute edits, and custom
   properties are all invisible, so the agent is told nothing changed.
2. The snapshot walks 24 datablock collections and builds per-object tuples
   (including a 16-value world matrix) **twice per call**, regardless of what
   the script touched. Cost grows with scene size on every exec call.
3. The agent cannot see detail. `render.review_set` offers only
   `camera/top/side/three_quarter` framed on scene or `show_only` bounds;
   `scene.screenshot` can orbit one object; `render.compare` only diffs
   equal-size PNGs, which is meaningless between a render and a reference
   photo. There is no orthographic view, no close-up of a region (e.g. the
   joint between trigger guard and receiver), and no render matched to a
   reference image. Exec cannot fill this safely: GPU/render calls from the
   bridge timer crash Blender (`project-context/sources/05-risks-and-gotchas.md`),
   so rendering must go through the existing deferred path.
4. The running setup does not use this repository (see Part D).

## Decided

- Optimize exec now; do not wait for call-log measurements. Performance is a
  requirement with a budget (Part B), measured by a benchmark.
- The bridge token threat model is unchanged and needs no work.
- An exec receipt must never claim "no change" when geometry, modifier
  properties, node trees, materials, or transforms changed.
- Visual review stays on the deferred GPU path. No render/GPU work from the
  bridge timer.
- Deployment (Part D) happens only after all tests in this plan pass.

## Part A: exec change detection

### Required coverage

Detect, per affected datablock, at least:

| Category | Examples |
|---|---|
| geometry | vertex positions, edges/faces topology, even with unchanged counts; curve points/handles; edit-mode meshes (sync edit-mode data before reading, or read via bmesh) |
| transform / hierarchy | world matrix, parent, collections |
| modifiers | add/remove/reorder, any property change, show_viewport/render |
| shading | material slots and assignment per face; material and world node trees (nodes, links, input defaults, node properties) |
| Geometry Nodes | node group trees and modifier inputs |
| UV / attributes | UV layers and data, color attributes, custom attributes, seams/sharp/crease/bevel weights |
| other | custom properties; datablock create/remove/rename (existing) |

Receipt fields (default mode), extending v0.6:

- `changes`: per category, affected names (capped as today), with a
  `geometry` entry saying e.g. `{"Receiver": "positions"}` or `"topology"`.
- `changed`: `true` when anything was detected. When nothing was detected,
  return `changed: false` **and** `"detection": "no_changes_detected"` — not a
  guarantee, since arbitrary Python can touch unobserved RNA. Keep bumping the
  epoch on every exec as today.

### Suggested approach (executor decides after measuring)

1. **Primary: depsgraph updates.** Register a temporary
   `bpy.app.handlers.depsgraph_update_post` handler around the exec, force
   evaluation after the script (`view_layer.update()` / evaluated depsgraph),
   and collect `depsgraph.updates` (`id`, `is_updated_geometry`,
   `is_updated_transform`, `is_updated_shading`). Cost is proportional to what
   changed, not scene size. Verify live that it fires for: bmesh
   `to_mesh` + `mesh.update()`, direct `mesh.vertices[i].co` writes,
   `foreach_set`, edit-mode `bmesh.update_edit_mesh`, modifier property
   writes, node edits, material assignment. Record which ones do not fire.
2. **Fallback for gaps found in step 1:** targeted fingerprints only for
   the categories depsgraph misses, e.g. a hash of
   `mesh.vertices.foreach_get("co")` (numpy, no Python loops), modifier
   property hash via `bl_rna.properties`, node tree hash (nodes, links,
   defaults). Compute fingerprints lazily: only for datablocks the script
   could have touched when that can be bounded, otherwise all meshes with a
   cheap pre-check (pointer + counts + `is_evaluated`-independent data).
3. Keep identity via `as_pointer()` but guard against pointer reuse after
   delete+create (compare name + type too) so a new datablock is not reported
   as a rename.

### Tests

- Unit (fake `bpy`): each category above produces the right `changes` entry;
  pointer reuse is not reported as rename; `detection` field semantics.
- Headless Blender 5.2 (`tests/run_python_exec_headless.py`): one exec per
  category that changes only that category, asserting it is detected; a
  pure-read exec reports `no_changes_detected`; an edit-mode bmesh edit is
  detected.

## Part B: exec overhead

- Remove redundant per-object fields (`location/rotation/scale` duplicate
  `matrix_world`).
- Use `foreach_get` on collections where Blender supports it instead of
  Python loops.
- Do not walk collections that cannot have changed when a cheaper signal
  (length, depsgraph updates) proves it.
- Report `timings_ms.exec_user` and `timings_ms.exec_overhead` (snapshot +
  diff) in the envelope meta so the call log records them.

**Budget** (exec with a trivial script, headless Blender 5.2, measured by a
new `tests/run_python_exec_benchmark_headless.py` and reported in the PR):

| Scene | Overhead budget |
|---|---|
| 1,000 objects, 1M vertices total | ≤ 30 ms |
| 10,000 objects, 5M vertices total | ≤ 150 ms |

If a budget cannot be met without losing Part A coverage, keep coverage,
report the measured numbers, and explain the trade-off.

## Part C: detail review renders

All through the existing deferred render/screenshot path, restoring scene,
camera, and visibility state afterward.

1. **Targeted close-up.** Frame a target that is an object, a set of objects,
   a world-space point + radius, or a bounding box (e.g. the joint between
   two parts). Options: view direction (named or vector), perspective or
   orthographic, isolation (`show_only` / hide others / keep context faded if
   cheap), resolution. Returns the PNG path and the camera parameters used,
   so a later render can reproduce the same view.
2. **Orthographic views.** Front, back, left, right, top, bottom, framed on the
   target, sharing one scale across views when requested (for proportion
   checks against drawings).
3. **Reference-matched render.** Given a reference image and either explicit
   camera parameters or an existing camera (the user or agent aligns it once),
   render at the reference's aspect ratio and output: the render, a
   side-by-side sheet, and an overlay (adjustable opacity or edge overlay).
   Do not attempt automatic camera solving in this plan.
4. **Contact sheet.** Combine several review PNGs with labels into one image,
   so the agent inspects many views at one image cost.
5. Extend `render.review_set` or add a new tool, whichever keeps schemas
   simpler; keep old view names working.

Tests: unit tests for framing math (point+radius, bbox, ortho scale sharing)
and sheet composition; headless 5.2 run producing each output type with
correct dimensions; a live GUI smoke (deferred path) with two concurrent
clients requesting close-ups, per the GPU risk rule.

  `%APPDATA%\Blender Foundation\Blender\5.2\scripts\addons\codex_blender_toolkit`
  has no `tools/python_exec.py` (pre-v0.6). A 5.1 copy also exists.

Steps:

   benchmark.
2. Point `PYTHONPATH` in `~/.codex/config.toml` at
   `<legacy-checkout>\mcp_server\src`. Edit only that value;

   5.2 (replace the old add-on folder). Leave 5.1 alone unless the Owner asks.

   `codex-blender` must be restarted (add-on modules stay cached otherwise).
5. After restart: `system.doctor` healthy, `adapter.schema_audit` aligned,
   add-on and adapter versions equal, `python.exec` listed, one real typed
   call and one `python.exec` call succeed, and a call-log file is written.
6. Consider making `system.doctor` warn when adapter and add-on versions
   differ or the adapter is loaded from outside the expected repository, so
   this drift is caught automatically next time.
