# Codex Blender Toolkit v0.4 Plan — Concurrency & Coordination

This plan covers three concurrency scenarios the current v0.3 architecture does
not yet coordinate:

1. Multiple Codex **conversations** driving one Blender.
2. One Codex run spawning multiple **sub-agents** that call tools in parallel.
3. Multiple **Blender instances** controlled at once.

## What already holds, and what breaks

The bridge already serializes every tool call on Blender's main thread
(`bpy.app.timers` drains the request queue), so individual dispatches never
interleave or corrupt `bpy` state, no matter how many clients connect. The gap
is a **coordination layer above dispatch**: identity, isolation, observability,
and instance addressing.

| Scenario | Current failure mode | Root cause |
| --- | --- | --- |
| Multi-conversation, one Blender | No crash, but concurrent writes to the same datablock are last-writer-wins; one client's `scene.save_version` silently switches the active document under another client | One shared token (bridge can't tell clients apart); no logical mutual exclusion; callers can't see which file/state they act on |
| Multi sub-agent | Same as above, plus **>16 concurrent connections are silently dropped** (17th connection closed with no response) and queued calls time out at 30s under load | No per-client fairness/backpressure; silent connection drop |
| Multiple Blender instances | Second bridge silently double-binds the same port (Windows `allow_reuse_address=True`); calls route to a random instance | Fixed port, no instance addressing |

The dangerous property across all three is **silent action on the wrong
target**, not a crash.

## Design principles

- Keep single-writer, main-thread serialization. Do not parallelize `bpy`.
- Add coordination **above** dispatch, not inside tool handlers.
- Trust boundary is the local machine / OS user. `client_id` is for attribution
  and coordination, not authentication; the shared/instance token remains the
  security boundary. Never store token values in the repo or these docs.
- Fail loud, never silent: contention, staleness, wrong-instance, and overload
  must return structured errors, not undefined behavior.

## Cross-cutting primitives (land in Phase 1)

- **client_id**: every bridge request carries an optional self-declared
  `client_id`. The `codex-blender-mcp` adapter generates a stable per-process id
  at startup (uuid4) and may append a per-call agent tag when Codex supplies
  one. Recorded in journals and used as the lease holder key.
- **state_token**: an opaque string encapsulating `(active_filepath,
  scene_epoch)`. `scene_epoch` is a monotonic integer bumped on every mutating
  dispatch (`material.patch` with changed=true, `scene.save_version`,
  `checkpoint.restore`) and whenever the bridge timer observes
  `bpy.data.filepath` change out-of-band (GUI file open). `scene.inspect`
  returns the current `state_token`; mutating tools accept an optional
  `expected_state`. If supplied and it does not match the current token →
  `StaleStateError` with zero change.

## Phase 1 — Observability + optimistic concurrency + safe multi-bind (foundation, unconditional)

Owner decision: optimistic-first is the confirmed starting posture.

1. `scene.inspect` returns `filepath`, `saved`/`dirty` state, and `state_token`.
2. All mutating tools accept optional `expected_state`; mismatch →
   `StaleStateError` (structured, zero change). This is lightweight optimistic
   concurrency: any agent that tries to write on a stale view is blocked at the
   moment of write.
3. Every request carries `client_id`; mutation journals record the acting
   client.
4. Remove `allow_reuse_address` (exclusive bind): a second bridge on an
   in-use port fails with a clear `InvalidStateError` instead of silently
   double-binding. (Distinct-port multi-instance is Phase 3.)
5. `bridge.status` / `session.whoami` returns instance identity: pid, active
   filepath, port, current `state_token`, connected-client summary.

Acceptance: two concurrent clients editing the same material — the second write
on a stale `state_token` is rejected; neither silently clobbers the other; each
call is attributable to its `client_id`; a second bridge on the same port fails
loudly.

## Phase 2 — Session leases + fairness (critical-section isolation)

Owner decision: add advisory-but-enforced leases after optimistic lands.

1. `session.acquire_lease(scope="document", ttl)` → `lease_id`, or
   `LockedError(held_by, expires_in)`. v0.4 scope is the whole document;
   datablock-scoped leases are a later refinement.
2. While a document lease is held, writes by a non-holder → `LockedError`;
   reads always proceed; the holder's own writes proceed. Pair a lease with the
   `checkpoint → patch → save_version` critical section.
3. TTL auto-expiry (enforced by the bridge timer) so a crashed/abandoned agent
   cannot deadlock the document. `session.renew_lease` / `session.release_lease`.
4. Fairness/backpressure: replace the silent >16-connection drop with a bounded
   accept returning explicit `BridgeBusyError` (with queue depth + retry hint);
   add a per-`client_id` in-flight cap so one chatty agent cannot starve others;
   surface queue depth in `bridge.status`.

Acceptance: an agent holding a document lease completes a multi-step repair
while a competing agent's writes are cleanly rejected with holder + expiry; the
lease auto-expires on TTL; a burst of concurrent callers degrades to explicit
busy responses, never silent drops.

## Phase 3 — Multi-instance addressing (confirmed in scope)

Owner decision: true multi-instance parallel control is required.

1. Distinct port per Blender instance (`start_bridge(port=...)` already
   supports this); the exclusive bind from Phase 1 guarantees clean per-port
   ownership.
2. **Instance registry**: each bridge records `{pid, port, filepath, started,
   token_location}` (never the token value) to a shared file, e.g.
   `~/.codex/codex_blender_instances.json`, and removes its entry on stop.
   bootstrap/Codex can enumerate live instances.
3. **Explicit instance selection at the MCP layer** (primary design): tools gain
   an optional `instance` selector (registry id or port); the `codex-blender`
   server routes to the matching bridge, defaulting to the sole registered
   instance for backward compatibility. Explicit per-call targeting is chosen
   over hidden per-client "active instance" state because multiple agents must
   be able to target different instances unambiguously and safely.
4. **First-class bridge start** as a Blender add-on UI panel (or add-on
   auto-start from a known token source) that starts/stops each instance's
   bridge on a chosen port and rotates its token without persisting or logging
   the value. The community Blender MCP add-on has already been uninstalled and
   the bridge is currently started manually from Blender's Python Console; this
   panel formalizes that per instance and is the clean multi-instance start
   mechanism.
5. `bridge_session.py` is reworked for multi-instance: it currently drives the
   now-removed community MCP socket on 9876 (stale) — replace that with the
   add-on panel / a direct start path, allocate/track a port per instance, and
   write one `codex-blender` config entry (or one server with the `instance`
   param) per live Blender.

Acceptance: two Blender instances run bridges on distinct ports; Codex
enumerates both from the registry and drives each independently by explicit
`instance`; a call to one never reaches the other; tokens remain per-instance
and out of the repo.

## Decisions locked (this plan)

- Isolation posture: **phased — optimistic (Phase 1) then enforced leases
  (Phase 2)**. (Owner, 2026-07-13.)
- Multi-instance: **in scope — Phase 3 implemented.** (Owner, 2026-07-13.)
- Keep main-thread serialization; coordination lives above dispatch.

## Open sub-decisions (Category B, resolved at brief time)

- Exact `state_token` encoding and whether epoch is per-document or global.
- Lease scope granularity beyond `document` (datablock/material-level).
- Config shape for multi-instance: one `codex-blender` server with an
  `instance` param vs. one server entry per instance. Primary is the single
  server + explicit `instance` param.

## Non-goals (v0.4)

- No distributed/multi-machine coordination (local OS user only).
- No parallel `bpy` execution.
- No cross-instance transactions (each instance is independent).
- Datablock-granular leasing (document scope first).
