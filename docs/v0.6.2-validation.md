# v0.6.2 validation

Date: 2026-09-24. Target: Blender 5.2.2 on Windows. The source at this
repository was used for each test. The GUI run used a separate factory-startup
Blender process and temporary scene; it did not inspect or change the Owner's
open document.

## Change detection and performance

`tests/run_python_exec_headless.py` exercises geometry edits with unchanged
counts, topology rewiring, direct and `foreach_set` vertex positions, edit-mode
bmesh, modifier RNA, material and World nodes, Geometry Nodes tree and exposed
modifier input, UV and attribute values, edge marks, transforms, custom
properties, and a pure-read exec. The pure read reports
`detection:no_changes_detected`; each exec advances the state epoch. The
depsgraph probe established that custom ID-property changes do not emit an
update, so the shallow snapshot retains a custom-property comparison.

The benchmark creates the scene outside the timed call and dispatches a
trivial exec. Three independent runs of
`tests/run_python_exec_benchmark_headless.py` produced:

| Scene | Overhead, ms | Median, ms | Budget, ms |
| --- | --- | ---: | ---: |
| 1,000 objects / 1 million vertices | 22.381, 15.157, 14.850 | 15.157 | 30 |
| 10,000 objects / 5 million vertices | 150.955, 142.409, 147.694 | 147.694 | 150 |

At 10,000 objects, two of three final runs met the 150 ms budget; the other
missed by 0.955 ms. The median met the budget, but the margin is narrow and
single-call latency can exceed it. We kept custom-property and modifier-input
coverage rather than removing those comparisons to manufacture a larger
margin. `meta.timings_ms.exec_user` and `exec_overhead` are exposed and
the MCP call log records them when present.

## Automated and live evidence

- Add-on unit suite: `python -m unittest discover -s tests -p 'test_*.py' -q`
  passed 233 tests after the Geometry Nodes input detection refinement.
- MCP suite, with `PYTHONPATH` set to this repository's `mcp_server/src`:
  `python -m unittest discover -s mcp_server/tests -p 'test_*.py' -q`
  passed 119 tests.
- Headless Blender 5.2.2: `--background --factory-startup --python-exit-code 1`
  with `tests/run_python_exec_headless.py`,
  `tests/run_detail_render_headless.py`, and
  `tests/run_adapter_live_headless.py` each exited 0. The detail run checked
  close-up, point/bounds, six orthographic views, reference render, side
  sheet, overlay, and labeled contact sheet outputs and dimensions.
- Live adapter audit in the isolated Blender process reported 142 add-on
  tools, zero schema errors and warnings, six call-log records, linked
  workflow child steps, and redacted token values.
- GUI Blender 5.2.2: `tests/run_deferred_render_gui_smoke.py` started two
  distinct bridge clients concurrently. Both deferred calls succeeded in
  4.308 seconds, wrote seven PNGs, restored camera, object visibility, and
  resolution, and removed the temporary camera. The process exited 0;
  [`result.json`](../tests/.tmp_gui_render_smoke/result.json) is the local
  machine-readable evidence.

## Local deployment

The 0.6.2 ZIP was built from this repository. The Codex
`[mcp_servers.codex-blender.env]` `PYTHONPATH` now points at this repository's
`mcp_server/src`. Only that value was edited; the prior config was backed up
as `config.toml.bak-v062-20260924-203437`. The Blender 5.2 add-on was
installed from the ZIP after backing up its 0.5.0 directory as
`codex_blender_toolkit.bak-v062-20260924-203437`. Blender 5.1 was not changed.

An isolated fresh Blender 5.2.2 process imported the **installed** add-on
from `%APPDATA%/Blender Foundation/Blender/5.2/scripts/addons`, reported
version 0.6.2, and returned a healthy `system.doctor`. A fresh host Python
adapter process imported from the newly configured `PYTHONPATH`; typed
`system.doctor` and `scene.inspect` succeeded, `python.exec` returned 42,
`adapter.schema_audit` found 142 tools and no errors or warnings, and the
call-log summary found recorded calls with no token in the log. Both add-on
and adapter reported exactly `0.6.2`. The runner was
`tests/run_installed_deployment_headless.py`; local result files are under
`tests/.tmp_deployment_verify/`.

The already-running Blender instance and any already-running Codex or Claude
MCP processes have not been restarted. They may still hold old modules until
restarted; the fresh-process test establishes the installed path and contract,
not their in-memory state.
