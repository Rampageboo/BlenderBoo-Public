# v0.7.1 Plan: Import Workbench Camera Handoffs; Fix Principal-Point Default

Status: Implemented in the source working tree, 2026-09-26. Small follow-up to v0.7
(`08b6f79`, `2ce30cf`). Camera solving stays in the separate Camera Refinement
Workbench; this toolkit only imports and uses its results.

Implementation note: the two existing workbench camera packages contain
`cameras.json` rather than `cameras.txt/images.txt`. The importer accepts those
packages directly and also accepts standalone COLMAP text models. An imported
RealityScan CSV with nonzero raw distortion is labeled diagnostic because
Blender cannot reproduce that distortion. Headless Blender passed both M4A4
packages (808 cameras, three projection checks each below 0.1 px); the source
MCP schema audit found 173 tools with zero errors and warnings. The currently
open Blender instances have not been restarted onto this source revision.

## Why

1. **The current default reproduces a known-bad camera mix.**
   `camera.import_photogrammetry` defaults to `mode="centered_zero"`
   (`tools/photogrammetry_import.py`, ~line 129): it keeps RealityScan poses
   and focal but drops RealityScan's solved principal point. The workbench
   measured exactly this mix on M4A4: median silhouette IoU 0.627 and ≈33 px
   boundary error, versus 0.977 / ≈1 px when intrinsics are kept as solved.
   Poses and intrinsics are one coupled solution. `AGENTS.md` and `CLAUDE.md`
   currently instruct the same wrong default.
2. **The conventions are now solved, but outside the toolkit.** The
   workbench's Track B reproduced RealityScan exactly from exported tracks
   (404 cameras, 71,639 points, 220,686 observations, 0.464 px median
   reprojection), established that exported `f`, `px`, `py` are normalized by
   `scale = max(width, height)`, and recorded the fixed translation between
   RealityScan's output and Euclidean systems. The toolkit's own CSV importer
   still treats its yaw/pitch/roll convention as provisional.
3. **Physically constrained cameras now exist.** Track B's plateau solve
   (centred principal point, zero distortion, one focal per zoom plateau)
   matches Track A in image space (51-frame median IoU 0.97617 vs 0.97614;
   mean boundary 0.98 vs 1.04 px). An independent zoom-anchor estimate puts
   the principal point at (1279.75, 534.73) px vs the image centre
   (1280, 535). The shared-focal variant failed (IoU 0.658), so the zoom is a
   FOV change, not a dolly.

## Decided

- The primary import path is the workbench **handoff package** (COLMAP text
  model, `PINHOLE`, plus per-camera metadata and scores), not the raw
  RealityScan CSV.
- Every imported camera set carries its kind: `reproduction` (Track A:
  intrinsics and poses exactly as the source solved them) or `constrained`
  (Track B: re-optimized with centred principal point). Intrinsics are always
  applied exactly as given by the package. The importer never replaces a
  principal point, focal, or pose from one set with another.
- Both sets may coexist in one scene in separate collections.

## Part A: `camera.import_colmap_package` (name is a proposal)

Input: package directory (as produced by the workbench, e.g.
`m4a4_track_a_source_world_export_v2` and `m4a4_track_b_square_plateau_export`),
optional image directory, optional object whose world transform maps the
package world frame into the scene (the packages keep their solved world
frame; mesh alignment is metadata), collection name, dry run.

Behavior:

- Read `cameras.txt` / `images.txt` (and optionally `points3D.txt` as a point
  object); support `PINHOLE` and `SIMPLE_PINHOLE`; refuse distortion models
  with a clear error (Blender cannot represent lens distortion).
- Convert COLMAP world-to-camera (quaternion + translation, OpenCV axes) to
  Blender camera objects (−Z forward, +Y up); focal via sensor width and
  horizontal fit; principal point via `shift_x`/`shift_y` including the
  aspect-ratio term for the vertical shift; render resolution from the
  camera size.
- Read the package's kind (`reproduction` / `constrained`) and per-camera
  scores; store them as custom properties (source frame, run id, kind, IoU,
  boundary error, focal, principal offset) so an agent can choose reference
  frames by score.
- Dry run reports counts, kind, frame range, score summary, and any cameras
  whose image file is missing.

Verification (required):

- Unit tests of the conversion with synthetic cameras: known 3D points
  project to the same pixel through the COLMAP model and through the created
  Blender camera (`world_to_camera_view`), including non-zero principal
  offsets and non-square image aspect (2560 × 1070).
- Headless test importing both M4A4 packages when present (skipped
  otherwise): 404 cameras each, correct kind labels, and the workbench's
  three-point projection check per camera within 0.1 px.

## Part B: fix `camera.import_photogrammetry` (RealityScan CSV)

- Change the default to keep the CSV's solved intrinsics (current
  `csv_principal` behavior); label the set `reproduction`.
- Keep `centered_zero` only as an explicit diagnostic mode whose receipt
  states that it mixes solved poses with unsolved intrinsics and is expected
  to misalign images.
- Where the pose convention is still provisional, point the receipt to the
  COLMAP package import as the verified path.

## Part C: instructions

Update `AGENTS.md` and `CLAUDE.md`: replace "use centered, zero-distortion
optics for game-capture images" with "apply camera intrinsics exactly as the
imported package gives them; a centred principal point is correct only for a
`constrained` set solved that way". Add that camera solving happens in the
Camera Refinement Workbench and the toolkit imports its packages. Also
update the corresponding lines in `docs/v0.7-creature-modeling-and-rig.md` if
they still describe the old default.

## Out of scope

Camera solving, bundle adjustment, zoom-anchor estimation, and mask
refinement (all in the workbench).
